# Функциональные требования к ядру оркестрации консолидированного заказа

## Функциональные требования

### 1. Управление консолидированным заказом

| ID | Требование |
|---|---|
| **ORC-001** | Система должна принимать единый формализованный запрос потребителя на получение одного или нескольких продуктов и сервисов ДЗЗ. |
| **ORC-002** | Система должна проверять обязательные параметры запроса и возвращать перечень ошибок без создания исполняемого заказа. |
| **ORC-003** | Система должна хранить связь консолидированного заказа с позициями, подзаказами, попытками исполнения и полученными результатами. |

### 2. Декомпозиция заказа клиента

| ID | Требование |
|---|---|
| **ORC-004** | Система должна автоматически разделять запрос потребителя на отдельные позиции и подзаказы по поставщикам. |
| **ORC-005** | В демонстрационном сценарии один консолидированный заказ должен включать подзаказы как минимум двум различным поставщикам. |
| **ORC-006** | Для каждого подзаказа система должна фиксировать поставщика, требуемый результат, плановый объём, единицу измерения, срок исполнения, обязательность позиции и условия приёмки. |
| **ORC-007** | Система должна поддерживать зависимости между подзаказами: независимое параллельное исполнение и запуск зависимого подзаказа после получения требуемого входного результата. |

### 3. Формирование и исполнение подзаказов

| ID | Требование |
|---|---|
| **ORC-008** | После подтверждения заказа система должна формировать отдельные подзаказы и направлять их выбранным поставщикам. |
| **ORC-009** | Система должна направлять независимые подзаказы поставщикам параллельно. |
| **ORC-010** | Система должна присваивать каждому подзаказу внутренний идентификатор и сохранять внешний идентификатор, полученный от поставщика. |
| **ORC-011** | Система должна фиксировать принятие, отклонение или запрос уточнения подзаказа поставщиком. |
| **ORC-012** | Система должна контролировать тайм-аут ответа, срок исполнения и другие формализованные условия каждого подзаказа. |
| **ORC-013** | Пользователь должен иметь возможность просматривать общий статус заказа, статусы подзаказов, общий прогресс, полученные результаты и зарегистрированные отклонения. |

### 4. Асинхронное взаимодействие

| ID | Требование |
|---|---|
| **ORC-014** | Система должна асинхронно получать изменения статусов посредством событий поставщика и/или периодического опроса его интерфейса. |
| **ORC-015** | Система должна сопоставлять каждое внешнее событие и каждый результат с конкретным консолидированным заказом, подзаказом и попыткой исполнения. |
| **ORC-016** | Повторно полученное событие не должно приводить к повторному созданию результата, повторному учёту объёма или недопустимому переходу состояния. |
| **ORC-017** | Система должна приводить внешние статусы разных поставщиков к единой внутренней модели состояний. |

### 5. Координация исполнения и проверка результатов

| ID | Требование |
|---|---|
| **ORC-018** | Система должна определять, какие подзаказы могут исполняться параллельно, а какие зависят от результатов предыдущих этапов. |
| **ORC-019** | Система должна определять готовность консолидированного заказа к следующему этапу на основании состояний обязательных подзаказов. |
| **ORC-020** | Система должна регистрировать переданный поставщиком результат вместе с метаданными и фактическим объёмом исполнения. |
| **ORC-021** | Система должна проверять целостность, формат, состав и соответствие результата условиям конкретного подзаказа. |
| **ORC-022** | Система должна сохранять успешно полученные результаты независимо от состояния остальных подзаказов. |

### 6. Количественный учёт и агрегация

| ID | Требование |
|---|---|
| **ORC-023** | Система должна вести по каждой позиции и каждому подзаказу плановый, переданный, принятый, отклонённый и неисполненный объём. |
| **ORC-024** | Единица количественного учёта должна задаваться для позиции заказа, например: км² покрытия, количество сцен, количество продуктов, объём данных или количество вызовов сервиса. |
| **ORC-025** | Общий исполненный объём должен рассчитываться только по принятым результатам. |
| **ORC-026** | Система не должна повторно учитывать один и тот же объём при повторной отправке результата, повторном исполнении или замене поставщика. |
| **ORC-027** | Система должна рассчитывать процент исполнения по каждой позиции и по консолидированному заказу на основании согласованного способа расчёта. |
| **ORC-028** | После получения обязательных результатов система должна сформировать единый комплект, включающий результаты, метаданные, опись и отчёт об исполнении. |

### 7. Обработка исключительных ситуаций и корректирующие действия

| ID | Требование |
|---|---|
| **ORC-029** | Система должна обнаруживать отказ, ошибку, нарушение условий или превышение времени ожидания по отдельному подзаказу. |
| **ORC-030** | Ошибка одного поставщика не должна отменять успешно исполненные подзаказы других поставщиков. |
| **ORC-031** | Если часть подзаказов исполнена, а один из обязательных подзаказов завершился ошибкой, система должна присвоить консолидированному заказу состояние «Частичный сбой». |
| **ORC-032** | Система должна фиксировать тип сбоя, источник, время, затронутый объём, сохранённые результаты и принятое решение. |
| **ORC-033** | При частичном сбое система должна выбирать допустимое корректирующее действие: повторить попытку, назначить альтернативного поставщика, запросить уточнение, продолжить без необязательной позиции либо передать решение пользователю или оператору. |
| **ORC-034** | Количество повторных попыток, интервалы, тайм-ауты и возможность замены поставщика должны задаваться правилами для соответствующего вида продукта или сервиса. |
| **ORC-035** | Замещающий подзаказ должен ссылаться на исходный сбойный подзаказ, а его результат должен учитываться вместо результата неуспешной попытки. |
| **ORC-036** | Если корректирующее действие изменяет подтверждённые потребителем стоимость, срок, состав или существенные характеристики результата, система должна запросить повторное подтверждение. |
| **ORC-037** | После исчерпания допустимых корректирующих действий система должна предложить принять допустимый частичный результат либо завершить заказ как неисполненный. |

### 8. Формализованные бизнес-правила и приоритеты

| ID | Требование |
|---|---|
| **ORC-038** | Система должна применять формализованные и версионируемые правила выбора поставщика, корректирующего действия и приоритета заказа. |
| **ORC-039** | При конкуренции заказов за ограниченный ресурс система должна формировать однозначный порядок исполнения на основании класса приоритета, срока, времени регистрации и других согласованных признаков. |
| **ORC-040** | Система должна сохранять версию применённого правила и объяснение причины выбора поставщика, приоритета или корректирующего действия. |

### 9. Уведомления и аудит

| ID | Требование |
|---|---|
| **ORC-041** | Система должна уведомлять пользователя о принятии заказа, существенном изменении срока, частичном сбое, необходимости решения и завершении заказа, а также вести историю переходов состояний и действий. |

## Итоговые состояния заказа

| Состояние | Условие присвоения |
|---|---|
| **Исполнен** | Получены и приняты все обязательные результаты либо их допустимые замены |
| **Частично исполнен** | Пользователь или заранее согласованное правило разрешили принять неполный комплект результатов |
| **Не исполнен** | Обязательные результаты получить не удалось, а допустимые корректирующие действия исчерпаны |

Состояние **«Частичный сбой»** является промежуточным: система сохраняет успешные результаты и пытается восстановить исполнение. Состояние **«Частично исполнен»** является окончательным.

## Границы и допущения

- Конкретные значения тайм-аутов, количества повторов и интервалов ожидания должны быть согласованы отдельно.
- Правила определения приоритета должны утверждаться владельцем системы.
- Автоматическая замена поставщика допускается только в пределах ранее подтверждённых пользователем условий.
- Изменение стоимости, срока или существенных характеристик результата требует повторного подтверждения.
- Внутренние алгоритмы и производственные процессы поставщиков не входят в область настоящих требований.
- Все решения системы, переходы состояний и изменения количественных показателей должны быть доступны для последующего аудита.
