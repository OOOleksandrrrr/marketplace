# Нефункциональные требования к ядру оркестрации консолидированного заказа

## Нефункциональные требования

### 1. Надёжность и доступность

| ID | Требование | Основание |
|---|---|---|
| **NFR-001** | Коэффициент готовности системы должен быть не менее `0,95`. Для ядра оркестрации показатель применяется при распределении общего требования ГИАС РКД между составными частями. | ТЗ, п. 3.5.3.1 |
| **NFR-002** | Среднее время восстановления работоспособного состояния после отказа должно составлять не более `8 часов`. | ТЗ, п. 3.5.3.2 |
| **NFR-003** | Отказ интеграции с одним поставщиком не должен останавливать исполнение независимых подзаказов других поставщиков. | Производное |
| **NFR-004** | После перезапуска система должна восстанавливать состояния консолидированных заказов, подзаказов, таймеров и незавершённых корректирующих действий. | Производное |
| **NFR-005** | Подтверждённый результат поставщика и принятый объём исполнения не должны теряться при отказе или перезапуске ядра оркестрации. | Производное |

### 2. Производительность

| ID | Требование | Основание |
|---|---|---|
| **NFR-006** | Не менее 95% запросов пользователя на просмотр карточки и статуса заказа должны обрабатываться не более чем за `2 секунды` без учёта времени ответа внешних поставщиков. | Предложение для макета |
| **NFR-007** | Регистрация нового заказа и возврат его идентификатора должны выполняться не более чем за `3 секунды` без учёта поиска предложений и ответов поставщиков. | Предложение для макета |
| **NFR-008** | Полученное событие поставщика должно быть зарегистрировано не более чем за `5 секунд`, а изменение статуса должно стать доступно пользователю не более чем за `10 секунд`. | Предложение для макета |
| **NFR-009** | Время ожидания ответа поставщика не должно входить во время обработки внутреннего API системы и должно контролироваться отдельным асинхронным таймером. | Производное |
| **NFR-010** | Производительность должна измеряться отдельно для внутренних операций системы и для полного сценария с учётом задержек внешних поставщиков. | Производное |

### 3. Масштабируемость

| ID | Требование | Основание |
|---|---|---|
| **NFR-011** | Макет должен поддерживать одновременное исполнение не менее `100` активных консолидированных заказов и не менее `200` связанных подзаказов без нарушения требований NFR-006–NFR-008. | Предложение для макета |
| **NFR-012** | Добавление нового поставщика должно выполняться через подключение интеграционного адаптера без изменения базовой модели жизненного цикла заказа. | Производное |
| **NFR-013** | Компоненты приёма событий, оркестрации и чтения статусов должны допускать горизонтальное масштабирование без повторного исполнения одной команды. | Производное |

Значения нагрузки в NFR-011 являются примером для макета. Рабочие значения должны определяться по ожидаемому количеству пользователей, заказов и поставщиков.

### 4. Отказоустойчивость и целостность данных

| ID | Требование | Основание |
|---|---|---|
| **NFR-014** | Повторная доставка одного события или результата не должна приводить к повторному переходу состояния, повторному созданию результата или двойному количественному учёту. | Производное |
| **NFR-015** | Каждая команда, направляемая поставщику, должна иметь идентификатор, позволяющий определить повторную отправку. | Производное |
| **NFR-016** | Переход состояния заказа, изменение количественного показателя и регистрация основания перехода должны сохраняться согласованно. | Производное |
| **NFR-017** | При временной недоступности поставщика сообщения на отправку должны сохраняться до успешной передачи, истечения срока или исчерпания допустимых попыток. | Производное |
| **NFR-018** | Система должна выявлять события, поступившие с нарушением ожидаемого порядка, и обрабатывать их без перевода заказа в недопустимое состояние. | Производное |

### 5. Совместимость и интеграция

| ID | Требование | Основание |
|---|---|---|
| **NFR-019** | Взаимодействие с поставщиками и компонентами экосистемы должно выполняться через документированные и версионируемые API. | ТЗ, пп. 3.2.1.2 и 3.2.1.4 |
| **NFR-020** | Внешние форматы запросов, статусов и результатов должны преобразовываться в единую внутреннюю модель заказа и подзаказа. | Производное |
| **NFR-021** | Добавление новой версии API не должно нарушать работу действующих интеграций в пределах установленного периода совместимости. | Производное |
| **NFR-022** | Ошибка формата сообщения поставщика должна локализоваться в соответствующем подзаказе и не должна приводить к остановке всего ядра оркестрации. | Производное |
| **NFR-023** | Результаты должны предоставляться через согласованные хранилища и стандартизированные веб-сервисы; для пространственных сервисов должны учитываться применимые стандарты OGC. | ТЗ, п. 3.2.1.2 |

### 6. Информационная безопасность и управление доступом

| ID | Требование | Основание |
|---|---|---|
| **NFR-024** | Доступ пользователей и компонентов к функциям оркестрации должен предоставляться только после идентификации и аутентификации через единый сервис экосистемы. | ТЗ, п. 3.2.1.2 |
| **NFR-025** | Операции просмотра, создания, подтверждения, изменения и завершения заказа должны быть доступны только ролям с соответствующими полномочиями. | Производное |
| **NFR-026** | При предоставлении результатов система должна учитывать пространственные и временные ограничения доступа, связанные с пользователем, заказом и продуктом. | ТЗ, п. 3.2.2.2 |
| **NFR-027** | Передача запросов, статусов, результатов и учётных данных между компонентами должна выполняться по защищённым каналам связи. | Производное |
| **NFR-028** | Секреты интеграции, токены и пароли не должны отображаться в пользовательских сообщениях или записываться в журналы в открытом виде. | Производное |
| **NFR-029** | Проектные решения по защите информации должны учитывать требования, указанные в ТЗ, включая приказ ФСТЭК России от 11.04.2025 № 117, в пределах применимости к проектируемой системе. | ТЗ, п. 3.2.1.4 |

### 7. Журналирование и аудит

| ID | Требование | Основание |
|---|---|---|
| **NFR-030** | Система должна вести журнал создания заказа, переходов состояний, обмена с поставщиками, решений бизнес-правил, корректирующих действий и получения результатов. | Производное |
| **NFR-031** | Запись аудита должна содержать время, инициатора, идентификаторы заказа и подзаказа, выполненное действие, предыдущее и новое состояние, а также основание изменения. | Производное |
| **NFR-032** | Записи аудита не должны изменяться или удаляться обычными пользовательскими операциями. | Производное |
| **NFR-033** | Временные метки компонентов и интеграционных адаптеров должны формироваться в согласованной шкале времени с указанием часового пояса. | Производное |
| **NFR-034** | По истории заказа должна обеспечиваться возможность восстановить причины выбора поставщика, назначения приоритета и перехода к корректирующему действию. | Производное |

### 8. Удобство использования и локализация

| ID | Требование | Основание |
|---|---|---|
| **NFR-035** | Взаимодействие потребителя и оператора с системой должно осуществляться через графический пользовательский интерфейс. | ТЗ, п. 3.6.1 |
| **NFR-036** | Надписи экранных форм и сообщения конечному пользователю должны быть на русском языке. | ТЗ, п. 3.6.2 |
| **NFR-037** | При некорректном вводе система должна показать понятное сообщение с указанием поля и причины ошибки и сохранить корректно введённые данные. | ТЗ, п. 3.6.3 |
| **NFR-038** | Карточка консолидированного заказа должна позволять отличать общий статус от статусов отдельных подзаказов и видеть влияние сбоя на общий результат. | Производное |
| **NFR-039** | Пользовательские сообщения не должны содержать внутренние коды поставщиков или компонентов без понятного текстового объяснения. | Производное |

### 9. Сопровождаемость и конфигурируемость

| ID | Требование | Основание |
|---|---|---|
| **NFR-040** | Тайм-ауты, количество повторных попыток, правила выбора поставщика и правила приоритетов должны настраиваться без изменения программного кода ядра. | Производное |
| **NFR-041** | Все изменения бизнес-правил должны версионироваться с сохранением автора, времени изменения и даты начала действия. | Производное |
| **NFR-042** | Для каждого интеграционного адаптера должны быть определены контракт API, схема преобразования статусов, правила обработки ошибок и процедура проверки работоспособности. | ТЗ, п. 3.2.1.4; производное |
| **NFR-043** | Система должна предоставлять технические показатели состояния: доступность компонентов, размер очередей, количество ошибок, время обработки и количество заказов по состояниям. | Производное |
| **NFR-044** | Технические инциденты должны сопровождаться диагностической информацией, достаточной для определения компонента, поставщика и затронутых заказов. | Производное |

### 10. Резервное копирование и восстановление

| ID | Требование | Основание |
|---|---|---|
| **NFR-045** | Данные заказов, подзаказов, количественного учёта, бизнес-правил и аудита должны включаться в резервное копирование и архивирование. | ТЗ, п. 3.2.1.4 |
| **NFR-046** | После восстановления должна сохраняться согласованность консолидированных заказов, подзаказов, попыток исполнения, результатов и количественных показателей. | Производное |
| **NFR-047** | Процедура восстановления из резервной копии должна проверяться в рамках испытаний, а результат проверки должен документироваться. | Производное из требований надёжности |
